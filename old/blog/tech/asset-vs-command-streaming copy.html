Asset streaming vs command streaming

Asset/data streaming does not strictly sit under command/API streaming. Both push work to the client GPU, but they operate at different abstraction levels and often hybridize in production systems.

Command/APIAsset/DataClient GPUHybrid

01 · Command / API streaming

Lower-level. Server sends graphics API instructions (draw calls, bindings, buffer updates, state). Client is largely a dumb executor replaying the stream on its GPU — remote-controlling the pipeline. Example lineage: intercept Vulkan/GL and forward.

02 · Asset / data streaming

Higher-level. Server sends resources (meshes, textures, materials, scene state). Client owns a full renderer that generates its own API commands. Server delivers what to render, not every how of each frame.

03 · Comparison

AspectCommand / APIAsset / Data
GranularityFine (API calls)Coarser (assets/chunks)
Client intelligenceLower (replay)Higher (own engine)
Bandwidth patternGreat for dynamic scenesGreat with LOD/progressive load
FlexibilityPrecise controlLarge/complex content
ComplexityHigh sync burdenAsset pipeline burden
Common inSpecialized remote render / some cloud gaming coresUnreal/Unity streaming, viz, web 3D

04 · Why it feels nested

Hybrids stream assets first, then lightweight command-like updates (“move object X”). Shared goal (avoid pixel streaming) causes people to lump them under “client rendering.”

05 · Bottom line

Asset streaming is a separate, often more practical strategy. Command streaming is specialized and lower-level. They complement; neither strictly contains the other. See also command streaming vision.

Thesis

Ship content when you have a client engine; ship API tape when you need remote pipeline control.

Takeaway

Choose abstraction level by product: games and viz usually win with assets + LOD; specialized remote GL needs true command streams.
