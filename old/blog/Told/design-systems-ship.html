Design systems that ship with the product

We do not maintain one mega-kit for every brand. Each product carries its own visual contract — living style guide, tokens, and components that match the job.

Tokens firstZero-build kitsLane separation

01 · Why not one system

TaxFort’s soft purple SaaS, QuickSnaps clay shadows, Amerimatter paper catalogs, and Boxed hard edges answer different users. Forcing one radius and one primary color dilutes every product.

02 · What “ships” means

A design system in this shop is a runnable folder: tokens CSS, component inventory, and enough docs to implement without a Figma archaeology expedition. Prefer zero-build HTML/CSS until a framework earns its keep.

04 · Rules that transfer

  • Tokens before hard-coded hex in components
  • Document do / don’t with the same severity as API contracts
  • Separate packages when aesthetics conflict
  • Blog posts reuse the product tokens so the log feels native

05 · Tech that supports design

  • MPA view transitions for intentional navigation
  • Static HTML kits before React extraction
  • Module federation labs where shells grow
  • Desktop mounts when the UX lives on the filesystem
Design bias

A design system is not a brand police badge. It is shipping infrastructure for a specific product. When the product’s job changes (catalog vs film vs vault), clone the kit — don’t dilute the original.

Takeaway

This blog is intentionally multi-skin: each technical log wears the system it describes. That is the point of what we are building — product-shaped design, not theme parks of components.
